# User Input PoC 자동화 검증 결과

## 2026-11-07 변경 전 검증

2026-11-07 · Windows x64 빌드 26200 · feat/user-input-ui

Node.js 22.23.4, pnpm 10.34.9, React 19.2.9, TypeScript 5.9.3, Vite 8.3.6.
프로젝트의 입력 처리 범위는 React 메인 화면에서 FE 제출 콜백까지다.
[상세기능 명세서](https://docs.google.com/spreadsheets/d/1c5geYDtLm2X5B9cZzp-b03OnzviUmuezXJ3GdCrov_I/edit)의 시트1에서 I-000~I-102 및 D-100을 확인했다.

## 실행 환경 및 명령

설치한 개발 의존성은 Vitest 5.1.0, jsdom 31.0.0, Testing Library React 16.3.3, DOM 10.4.2, user-event 14.6.8, jest-dom 7.0.1이다.
테스트 환경은 vitest.config.ts와 tests/setup.ts로 구성한다. 테스트마다 DOM을 정리하며 사용자 이벤트 세션과 제출 스파이를 새로 생성한다.

프로젝트 루트에서 프로젝트 로컬 도구로 실행한다.

    .\scripts\dev-env.cmd pnpm exec tsc --noEmit -p tsconfig.test.json
    .\scripts\dev-env.cmd pnpm test
    .\scripts\dev-env.cmd pnpm build

변경을 감시하려면 pnpm test:watch를 사용한다.

## 기능별 자동화 검증

tests/user-input.test.tsx의 테스트 이름 앞에 명세서의 TC ID를 표기했다. I-100의 18~20은 탭 단독, 피부색 변경 이모지, 키캡 이모지를 추가한 회귀 케이스다.

| 기능 ID | TC 범위 (끝 두 자리) | 테스트 수 | 통과 | 실패 | 미검증 |
|---|---|---:|---:|---:|---:|
| I-000 | 01~03 | 3 | 3 | 0 | 0 |
| I-001 | 01~06 | 6 | 6 | 0 | 0 |
| I-002 | 01~04 | 4 | 4 | 0 | 0 |
| I-100 | 01~20 | 20 | 20 | 0 | 0 |
| I-101 | 01~03 | 3 | 3 | 0 | 0 |
| I-102 | 01~06 | 6 | 6 | 0 | 0 |
| 합계 | | 42 | 42 | 0 | 0 |

Vitest 실행 결과 42건 모두 통과했다(16.57초). 이모지 단독 입력은 편집 가능하며 버튼 클릭과 폼 직접 제출 경로에서 모두 차단된다. 다국어 및 유효한 혼합 입력은 앞뒤 공백과 줄바꿈까지 그대로 전달됐다. 검증한 범위에서 제품 결함은 발견되지 않았다.

## 타입 검사 및 빌드 결과

테스트와 제품 코드를 포함한 TypeScript 검사 및 pnpm build가 모두 종료 코드 0으로 완료됐다. Vite가 모듈 19개를 변환해 dist에 결과물을 생성했다. Tauri CLI 2.12.4 실행도 확인했다.

초기 설치에서 기존 node_modules의 전역 저장소 경로와 프로젝트 로컬 저장소 경로가 달라 ERR_PNPM_UNEXPECTED_STORE가 발생했다. 프로젝트 캐시에 기존 의존성 일부를 보관하고 기존 잠금 파일로 로컬 저장소에서 복원한 뒤 승인된 개발 의존성을 설치했다.

## 기존 검증

기존 제품 TypeScript 검사(pnpm exec tsc --noEmit) 통과. 프로젝트 캐시에 보관된 직전 브라우저 검증(check-emoji.html)을 실제 Edge에서 재실행해 VAL-001~014가 모두 통과했다. 이 결과는 위 신규 테스트 합계와 별개다.

## 정책 및 수동 확인

특수기호와 이모지만 섞인 입력의 제출 허용 여부는 이번 명세에서 미확정이다. 이 조합에 대한 통과 조건을 두지 않았다.
한글 문자열 입력·표시와 실제 Windows IME 조합은 검증 범위가 다르다. 자모 조합 중 글자 누락, 조합 확정 Enter의 의도치 않은 제출 여부는 Tauri 창에서 별도로 확인한다.

## 2026-11-08 수동 테스트 반영 및 회귀 검증

사용자가 실제 Tauri 앱에서 기록한 **수정 전** 결과는 14건 중 12건 통과, 2건 실패(85.7%)였다. MT-01~03, MT-05~12, MT-14는 통과했고 MT-04와 MT-13은 실패했다. 아래 결과는 수정 후에 별도로 실행한 검증이다.

### BUG-001 · MT-04 · I-001 / I-100 / D-100

**수정 완료 및 검증 통과.** 기존 검사는 이모지를 지운 후 공백 외의 내용이 남으면 허용했고 TC-I-100-14도 특수기호 단독 제출을 허용하는 이전 정책을 검사했다. 이번 정책에 맞춰 해당 기대값을 비활성화로 변경했다. isValidUserInput은 키캡을 포함한 이모지를 제외한 뒤 Unicode Letter 또는 Number가 남는지 검사한다. 버튼과 폼 제출 방어 코드는 같은 파생값을 사용하며 제출 콜백에는 원문을 전달한다.

| 회귀 ID | 검증 내용 | 결과 |
|---|---|---|
| REG-001~006 | 기호, 문장부호, 이모지, 기호·이모지 혼합, 키캡, 복합 이모지 차단 | 모두 통과 |
| REG-007~013 | 한글, 영어, 일본어, 한자, 숫자, 문자·기호 및 문자·이모지 조합 허용 | 모두 통과 |
| REG-014~016 | 전체 삭제 후 비활성화, 직접 제출 차단, 공백 포함 원문 보존 | 모두 통과 |

### BUG-002 · MT-13 · I-000

**코드 수정 완료 / 수동 재검증 필요.** 페이지 상하 여백이 각각 최소 40px이고, 제목 아래 36px 여백과 6줄 입력창이 유지되어 낮은 창에서 버튼이 첫 화면 아래로 밀렸다. 기존 CSS에는 세로 스크롤을 차단하는 규칙이 없었다. 기존 jsdom 테스트는 실제 창 크기나 렌더링 위치를 측정하지 않았다.

높이 480px 이하에서만 세로 여백·간격·입력창 높이를 줄였다. 단일 그리드 열이 좁아질 수 있게 하고 좁은 창에서 제목 줄바꿈을 허용했다. 문서의 기본 세로 스크롤과 입력창 크기 조절을 유지했다.

| 실제 Tauri 개발 앱의 WebView 크기(CSS px) | 수정 후 확인 |
|---|---|
| 1024×768, 800×600, 480×360 | 각 크기에서 입력 후 Tab으로 버튼에 포커스, 버튼 전체 표시, 클릭 제출 및 FE 수신 확인 |
| 300×180 | Tab으로 112px 세로 스크롤 후 동일 검증 통과 |
| Windows 최소 트래킹 크기(외곽 170×47 물리 px) | 클라이언트 영역 152×0 물리 px. 내용이 표시되지 않아 조작 불가 |

앞의 네 크기에서 수평 넘침과 입력창·버튼 겹침은 없었다. 검증은 별도의 Tauri 디버그 앱에서 네이티브 창 크기를 조정하고 실제 WebView2의 포커스·요소 위치·클릭 결과를 측정했다. 최소 크기에서도 조작을 보장하려면 창 설정의 최소 콘텐츠 크기 도입이 필요하다. 검증한 300×180 논리 px를 후보로 제안한다. 설정 변경 시 실제 창 테두리를 드래그해 최소 크기와 접근성을 재검증한다.
